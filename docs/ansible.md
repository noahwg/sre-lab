# Ansible configuration

Terraform builds the host; Ansible configures it. There is no SSH: Ansible connects over SSM Session Manager using the `community.aws.aws_ssm` connection plugin, with file transfer through the S3 bucket Terraform creates.

## Layout

```
ansible/
  ansible.cfg           inventory path, roles path, become on
  requirements.txt      Python deps (installed into ../.venv)
  requirements.yml      collections (amazon.aws, community.aws, community.general, ansible.posix)
  site.yml              top-level playbook
  inventory/hosts.yml   GENERATED by `make up` (git-ignored)
  roles/
    base/               telemetry volume, swap, system hygiene, Docker
    postgres/           Postgres 17 in Docker, private `db` network, runtime role
    monitoring/         VictoriaMetrics, VictoriaLogs, VictoriaTraces, Fluent Bit, node_exporter, Grafana
    edge/               Caddy: TLS (Let's Encrypt) and reverse proxy
    app/                the shortener container, pulled from ECR
```

Still to come in `monitoring`: a Postgres exporter.

## Usage

Python deps (`ansible-core`, `boto3`, `botocore`) are listed in `ansible/requirements.txt` and installed into a repo-local `.venv`. The Makefile puts `.venv/bin` on `PATH` for you, so there is nothing to activate. You still need the AWS CLI and `session-manager-plugin` installed system-wide.

```sh
make deps                          # one-time: creates .venv, installs Python deps and collections
make ping                          # verify the SSM connection
make check                         # drift check (--check --diff); run AFTER the first configure
make configure                     # apply everything
make configure ANSIBLE_ARGS="--tags swap"   # apply part of a role
```

The inventory supplies `telemetry_volume_id`, `telemetry_mount_point`, `primary_fqdn` and `fqdns` per host (see [terraform.md](terraform.md#the-inventory-stack)).

## Role: base

| Tag | What it does |
|---|---|
| `telemetry_volume` | Finds the EBS volume by ID (`/dev/disk/by-id/nvme-Amazon_Elastic_Block_Store_<id>`), creates an XFS filesystem **only if the device has none**, and mounts it at `telemetry_mount_point` with `noatime,nofail` |
| `swap` | 2 GB swap file on the root disk, persisted in fstab, `vm.swappiness=10` (the host has 2 GB of RAM) |
| `system` | chrony time sync, `dnf-automatic` for security-only updates, journald capped at 200 MB |
| `docker` | Docker from the AL2023 repos, pinned Compose v2 plugin, daemon `json-file` log rotation (10 MB x 3) and `live-restore` |

Defaults live in `roles/base/defaults/main.yml` (swap size, Compose version, journald cap, and so on).

### Notes

- **Idempotent.** A second run should report `changed=0`. Treat anything else as a bug.
- **Telemetry volume is safe to re-run.** The filesystem task never reformats a device that already has a filesystem, and `nofail` keeps the host booting if the volume is ever missing.
- **Compose plugin is downloaded** from the Docker GitHub release at a pinned version. Adding a checksum is a good follow-up.
- Docker's log driver is `json-file` for now. It will change once VictoriaLogs is running.

## Role: postgres

Runs Postgres in Docker from `/opt/postgres`. The app connects to it over the private `db` network (see the app role).

- **Private by construction.** It publishes no ports and sits on a Docker network named `db` marked `internal`, so it has no route in or out except to containers that join that network (the app will). Caddy is not on it.
- **Sized for a 2 GB host.** `mem_limit` 384 MB, `shared_buffers` 96 MB, 20 connections, `cpu_shares` 512 (a relative weight under contention, deliberately not a pinned core). Tunables are in `roles/postgres/defaults/main.yml`.
- **Two roles.** `shortener_owner` is the superuser created at first start; it will run migrations. `shortener_app` is what the app connects as: it can connect and read/write tables, but cannot create or drop anything. Default privileges mean tables created later by migrations are usable by the app role automatically.
- **Passwords** come from SSM (`/sre-lab/postgres/owner_password` and `.../app_password`, created by the secrets stack) and are read on your machine. The role refuses placeholder, short or non-alphanumeric values. The app password is re-synced to the database on every run, so rotating it is: change it in SSM, `make configure ANSIBLE_ARGS="--tags postgres"`. The owner password is only read on first start, so changing it later in SSM does nothing.
- **Data** lives in `/var/lib/postgres` on the root disk, so `make destroy` deletes it. Backups to S3 are the planned fix.
- The last two tasks wait for `healthy` and then log in as the app role over TCP (password authentication) to prove it works.

```sh
make secrets-up                    # creates the two new parameters (placeholders)
# set both to real values, e.g. aws ssm put-parameter --name /sre-lab/postgres/owner_password \
#   --type SecureString --overwrite --value "$(openssl rand -hex 24)"
make configure ANSIBLE_ARGS="--tags postgres"
# on the host: sudo docker exec -it postgres psql -U shortener_owner -d shortener -c '\du'
```

## Role: monitoring

Metrics and dashboards, in Docker from `/opt/monitoring`, with data on the telemetry volume (`/var/lib/telemetry/monitoring`). Runs after `app`.

| Container | Memory | What it does |
|---|---|---|
| `victoriametrics` | 160 MB | Stores metrics (30 days) and does the scraping itself, so there is no separate vmagent |
| `node-exporter` | 32 MB | Host CPU, memory, disk and load, read through a read-only view of `/` |
| `victorialogs` | 128 MB | Stores logs (14 days) |
| `victoriatraces` | 128 MB | Stores traces (7 days, hard-capped at 2 GiB on disk). Accepts OTLP/HTTP at `victoriatraces:10428/insert/opentelemetry/v1/traces` on the `edge` network, so the app can reach it |
| `fluent-bit` | 48 MB | Reads every container's Docker log file and ships it to VictoriaLogs |
| `grafana` | 384 MB | Dashboards, provisioned from files in the repo |

- **Scrape targets** (every 15 s, over the shared Docker networks): VictoriaMetrics itself, node-exporter, the app's `/metrics`, and Caddy. Caddy serves its metrics on `http://caddy:9180/metrics`, a listener that is not published, so only containers on the `edge` network can reach it. The public `/metrics` still returns 404. The list is `monitoring_scrape_targets` in the role defaults.
- **Exposure.** Grafana is public at `https://grafana.<primary domain>` (an `edge_sites` entry in `group_vars/all.yml`; Caddy proxies to `grafana:3000` and gets its own certificate), protected only by Grafana's login (sign-up and anonymous access are off). This is a deliberate lab trade-off; remove that entry to make it private again. VictoriaMetrics is **never** public. Both are also published on the host's loopback, reachable with an SSM port-forward:

  ```sh
  make grafana      # http://localhost:3000 (optional now that it is public)   user: admin, password: /sre-lab/monitoring/grafana_admin_password
  make vmui         # http://localhost:8428/vmui   (query and explore raw metrics)
  ```

- **Logs.** Fluent Bit tails `/var/lib/docker/containers/*/*-json.log` (its read offsets are kept on the telemetry volume, so a restart doesn't re-send) and posts JSON lines to VictoriaLogs. Each service's compose file asks Docker's `json-file` driver to record the `com.docker.compose.service` label, which becomes the `service` field. JSON log lines (the app, Caddy) are parsed so their fields are searchable; the log message is `fields.message`, `message` or `msg`, whichever exists. Fluent Bit's own logs are dropped so an error can't feed itself. Browse them on the **Logs** dashboard (filter by service and level, plus a case-insensitive regex search; volume charts and the log stream) or in Grafana Explore with the VictoriaLogs datasource; the Shortener dashboard also has two log panels. Queries are written in LogsQL, for example `service:shortener level:ERROR`. The VictoriaLogs UI is on `127.0.0.1:9428/select/vmui` (SSM port-forward). Docker's own rotation (`docker_log_max_size` x `docker_log_max_file`) still bounds the raw files on the root disk.
- **Traces.** Grafana's built-in Jaeger datasource (`VictoriaTraces`) queries VictoriaTraces's Jaeger-compatible API (`/select/jaeger`), so no plugin is needed. A new trace becomes searchable after roughly 30 seconds (`-search.latencyOffset`). Retention is 7 days and `-retention.maxDiskSpaceUsageBytes` caps storage, so a traffic burst can't fill the telemetry volume. The app sends its traces to `victoriatraces:10428` over the shared `edge` network (`app_otel_endpoint`, empty to turn tracing off; `app_otel_sample_ratio` to keep only a fraction). Browse them on the **Traces** dashboard (recent traces with Operation, Tags and Min duration filters, plus failed and slow request tables); click a trace ID to open its span waterfall in Explore. Tags use logfmt, e.g. `http.response.status_code=404`.
- **Grafana plugin.** The VictoriaLogs datasource is a plugin, installed once per pinned version (`monitoring_victorialogs_plugin_version`) by a one-off `grafana cli` run into the data directory. Grafana's default preinstalled apps stay off (`GF_PLUGINS_PREINSTALL` would add to them, not replace them).
- **First deploy recreates every container.** The `logging:` options changed on every service in every compose file, so the first run after this change recreates Caddy, the app, Postgres and the monitoring containers (a few seconds of downtime each; Postgres data is on a host path and survives).
- **CPU.** The Victoria containers are pinned to core 1 (`monitoring_cpuset`) with a low relative weight, so background merging can't starve Caddy and the app. Set `monitoring_cpuset: ""` to turn pinning off.
- **Dashboards as code.** `roles/monitoring/files/dashboards/*.json` (Host, Shortener, Logs and Traces) are copied to the host and re-read by Grafana every 30 s, so editing a file and running `make configure ANSIBLE_ARGS="--tags monitoring"` is all it takes. Datasources are provisioned too: VictoriaMetrics (as a Prometheus datasource) and CloudWatch, which supplies the CPU credit panels (credentials come from the instance role).
- **Password.** Read from SSM on your machine. Grafana only uses it when it first creates its database; rotate later with `docker exec grafana grafana cli admin reset-admin-password <new>`.
- **Checks at the end of the run:** the telemetry volume must be mounted (otherwise metrics would silently land on the root disk), VictoriaMetrics and Grafana must answer, **every** scrape target must be up (`sum(up)` equals the number of targets), logs must be arriving in VictoriaLogs, and Grafana must be able to query VictoriaMetrics, VictoriaLogs and VictoriaTraces.

```sh
make configure ANSIBLE_ARGS="--tags monitoring"
# Caddy changed too (metrics listener), so on the first run also apply the edge role:
make configure ANSIBLE_ARGS="--tags edge,monitoring"
```

## Role: edge

Runs Caddy in Docker from `/opt/edge` and gets a Let's Encrypt certificate for each site automatically (HTTP-01 over port 80, which the security group already allows). Certificates and the ACME account are stored in `/var/lib/caddy` on the root disk.

| Variable | Default | Purpose |
|---|---|---|
| `edge_sites` | `[{host: primary_fqdn, upstream: ""}]` | Sites to serve. Empty `upstream` returns a placeholder; set e.g. `shortener:8080` to reverse-proxy |
| `edge_acme_staging` | `true` | Use the Let's Encrypt **staging** CA (untrusted by browsers, generous rate limits) |
| `edge_acme_email` | `""` | Optional expiry-notice address |
| `edge_caddy_image` | `caddy:2.10-alpine` | Pinned image |
| `edge_network` | `edge` | Shared Docker network; the app and monitoring projects join it as an external network |

Notes:

- **Prerequisite:** the DNS records from `make up` must already resolve to the host's Elastic IP, or issuance fails.
- **Going to a real certificate:** once the staging run works, `make configure ANSIBLE_ARGS="--tags edge -e edge_acme_staging=false"`. To make it permanent, set the variable in `ansible/group_vars/all.yml`.
- `/metrics` is answered with a 404 at the edge. Metrics are scraped on the internal Docker network: Caddy's own metrics are on an unpublished `http://:9180` listener (see the monitoring role).
- A Caddyfile-only change is applied with an in-place `caddy reload`, not a restart.
- **Switching between staging and production:** Caddy keeps serving any valid certificate it already has, whichever CA issued it. The role therefore deletes certificates from the CA you are *not* using and restarts Caddy so it obtains a new one. Flipping back to staging removes the production certificate too, so do that only for testing.
- The last task probes each site over HTTPS from the host (retrying while the certificate is issued) and fails the run if nothing answers.

### Verify

```sh
make configure ANSIBLE_ARGS="--tags edge"
curl -sk https://<primary_fqdn>/                 # "sre-lab edge ok" (-k while on staging)
curl -s -o /dev/null -w '%{http_code}\n' http://<primary_fqdn>/   # 308 redirect to https
openssl s_client -connect <primary_fqdn>:443 -servername <primary_fqdn> </dev/null 2>/dev/null | openssl x509 -noout -issuer
```

The staging issuer name contains "(STAGING)".

## Role: app

Deploys the shortener image from ECR behind Caddy. The deployed version is the single variable `app_image_tag` in `ansible/group_vars/all.yml` (format `shortener-<full commit sha>`), so what's running is recorded in git. Deploying a new build means changing that line; **rolling back means pointing it at an older tag**.

What it does, in order:

1. Refuses to continue unless `app_image_tag` is well-formed.
2. On **your machine**, using your AWS credentials: looks up the account ID (to build the ECR address) and reads the API key from SSM Parameter Store (`/sre-lab/shortener/api_key`). It refuses to deploy if the value is the `REPLACE_ME` placeholder or shorter than 16 characters. The instance role has no access to the parameter.
3. On the host: logs Docker in to ECR using the instance role, writes `/opt/shortener/app.env` (root only, mode 0600; the key never appears in Ansible output), and renders a compose file.
4. Starts the container on the shared `edge` network with no published ports, a 64 MB limit, a read-only filesystem, all capabilities dropped, and a healthcheck.
5. Waits for the container to report `healthy`, then checks `/healthz` and `/readyz` end to end through Caddy.

**Migrations.** Before the app starts, the role runs `shortener migrate` from the image being deployed, as a one-off container on the `db` network, as the Postgres owner role (password read from SSM on your machine and passed through the environment). It is idempotent and reports `changed` only when it applied something. To apply migrations without redeploying the app: `make migrate`. This needs the Postgres container running and an `app_image_tag` whose image contains the `migrate` subcommand.

```sh
make migrate                                  # apply pending migrations only
make deploy                                   # deploy the tag in group_vars/all.yml
make deploy APP_TAG=shortener-<sha>           # one-off override, e.g. a rollback
```

`group_vars/all.yml` also sets `edge_sites` to proxy to `shortener:8080`. That change is applied by the `edge` role, so the **first** deploy needs `make configure ANSIBLE_ARGS="--tags edge,app"`. Later deploys only need `make deploy`.

Links are stored in Postgres. The app joins the `db` network and connects as the restricted `shortener_app` role: the role reads its password from SSM and writes `DATABASE_URL` into the root-only `app.env`. Deploying therefore needs the `postgres` role to have run first (`make configure` does this in order).

### Try it

```sh
KEY=$(aws ssm get-parameter --name /sre-lab/shortener/api_key --with-decryption --query Parameter.Value --output text)
FQDN=$(terraform -chdir=terraform/env/labs/dns output -raw primary_fqdn)

curl -sk -XPOST https://$FQDN/api/links -H "x-api-key: $KEY" -H 'content-type: application/json' \
  -d '{"url":"https://example.com"}'
curl -skI https://$FQDN/<code>                # 302 to https://example.com
```
